First, a distinction. When every prompt contains all the documents, and the documents contain every answer, the model does not need to know anything. It only needs to find the answer in the text. That task is called reading comprehension. When the model gets only the question, it must know the answer. That is closed-book question answering. Today we look at the case in between: the model gets the question, plus the documents that a program found for it. That is open-book question answering.

In Session 1 you also ran the quiz closed book. In our test run, the model got 2 of 8 right without the documents, and 8 of 8 with them. And the wrong answers sounded just as sure as the right ones. It even called today's technique Retrieval-Augmented Learning. A confident wrong answer like this is called a hallucination.

So a small model on its own is not a reliable source of facts. The documents supply the facts. Retrieval is how a system chooses which documents to give the model for each question.

  • Step 1: find the documents most related to the question. Step 2: put them into the prompt, next to the question.
  • The model answers from the prompt and from what it learned in training
  • The facts only need to be in a document the retriever can find: a small model can answer about facts it never saw in training

Lewis et al., “Retrieval-augmented generation for knowledge-intensive NLP tasks,” NeurIPS 2020

This technique is called RAG. It stands for retrieval-augmented generation. The main paper is by Lewis and colleagues, from 2020.

It has two steps. Step one: a program called a retriever searches a collection of documents and finds the ones most related to the question. Step two: the text of those documents is put into the prompt, next to the question. The prompt is the only way to give the model anything. Then the model writes the answer.

The model uses the prompt, and it still uses what it learned in training. Retrieval adds facts to the prompt. It does not switch off what the model learned.

Why is this useful? The facts do not need to be inside the model. They only need to be in a document that the retriever can find. So a small model can answer questions about facts it never saw in training. The questions for today are how well the retriever finds the right document, and what this saves.

  • The collection, the knowledge base: help-desk articles, contracts, regulations, …

A natural question is: how does the model know where to search? The answer is that the model does not search at all. Retrieval is a separate program that runs before the model. The people who build the system decide which documents it can search.

This happens in two phases. Phase one happens once, before any user asks anything. The builders collect the documents. For example, a company's help-desk articles, a law firm's contracts, or a university's regulations. This collection is called the knowledge base. Long documents are cut into smaller parts, called chunks. Each chunk is turned into an embedding, a vector that represents its meaning. The embeddings are stored in an index, together with the text of each chunk.

Phase two happens every time a user asks a question. The question is turned into an embedding too. The index is searched for the chunks whose embeddings are closest to the question's. Those chunks are pasted into the prompt, above the question. Then the model reads the prompt and writes the answer.

The model never sees the search. From its side, it just receives a question with some text attached.

The same idea in a chat assistant

2. The program around the model runs a web search and copies text from the top pages
3. The prompt now holds: the company's instructions + your question + the page text

  • It was trained on examples where a question about a specific or recent fact is followed by a search request
  • An uploaded file works the same way: cut into chunks, embedded, searched
  • Real systems add: approximate search over millions of chunks, word and embedding search together, a second model that reorders the top results

Let's see the same idea in a chat assistant you know. Suppose you ask: how much energy does one Gemini prompt use? We saw the answer in Session 1, from Google's own measurement.

Step one. The model does not answer yet. It writes a search request, for example: Gemini prompt energy. Step two. The program around the model sends this request to a web search engine, and copies text from the top pages. Step three. That text is added to the prompt. Now the prompt holds the company's instructions, which you do not see, your question, and the text of the pages. Step four. The model reads this prompt and writes the answer, with links to the pages it used.

How does the model decide to search? The model can only write text. A search request is also text, in a special format that the program around it recognizes. During training, the model saw many examples where a question about a specific or recent fact was followed by a search request. So for a question like ours, the most likely thing to write first is a search request. For "write me a poem", it is the poem.

Uploaded files work the same way. A long contract is cut into chunks, the chunks are embedded, and the chunks closest to your question go into the prompt.

Real systems add a few things. With millions of chunks, comparing the question with every chunk is too slow, so the search is approximate: it checks only the most promising chunks, and can occasionally miss the best one. Many systems search by words and by embeddings together, and merge the results. And often a second, more careful model reorders the top twenty to fifty results, and only the best few go into the prompt.

Step 2 · Dense retrieval

How a retriever finds documents

The cosine similarity of Session 1, for whole texts

  1. Turn every document into a vector, an embedding. Once, in advance.
  2. Turn the question into a vector, with the same model
  3. Compare the question's vector with each document's: cosine similarity
  4. Keep the k most similar documents. Only those go into the prompt.

cos(q, d) = q · d|q| × |d|

  • q · d: multiply matching values, add them up
  • |q|: the length of the vector, √(sum of squares)
  • 1: the same direction; 0: a right angle

How does the retriever decide which documents are relevant? It uses embeddings, which we saw in Session 1. An embedding is a vector, a list of values, that represents the meaning of a text. Texts with similar meanings get similar vectors.

The retriever computes one embedding for each document. This is done once, in advance. For each question, it computes the question's embedding, with the same model. Then it compares the question's vector with each document's vector.

The comparison is cosine similarity, the measure we used for aunt, uncle and car in Session 1. Multiply the matching values and add them up: that is the dot product. Then divide by the lengths of the two vectors. A value of 1 means the two vectors point in the same direction. A value of 0 means they are at a right angle: unrelated.

The retriever keeps the k documents with the highest values. In today's notebook, k is 2. The next screen works one example out.

Ranking documents by cosine similarity

Notebook 03b's toy vectors; the question “what does it cost in electricity to get an answer”

Here is one example, worked out, on three of the five toy documents. The other two, retrieval and quantize, point away from the question; the next panel shows all five. Real embeddings have hundreds of dimensions. These have two, so we can draw them and do the arithmetic. They are the toy vectors of the Retrieval Playground notebook.

Each document's vector is the average of the vectors of the words we know. The question is "what does it cost in electricity to get an answer". The only word with a vector is electricity, so the question's vector is 4, 3.

First the energy document, vector 4, 2. The dot product: 4 times 4 plus 3 times 2. That is 16 plus 6, which is 22. The length of the question: the square root of 4 squared plus 3 squared, the square root of 25, which is 5. The length of the document: the square root of 4 squared plus 2 squared, the square root of 20, about 4.47. So the cosine is 22 divided by 5 times 4.47. That is 22 divided by 22.35, about 0.98.

The carbon document, vector 3, 4: 4 times 3 plus 3 times 4 is 24. Its length is 5. 24 divided by 25 is 0.96.

The water document, vector 2.5, 3.5: 4 times 2.5 plus 3 times 3.5 is 10 plus 10.5, which is 20.5. Its length is about 4.30. 20.5 divided by 21.5 is about 0.95.

The energy document is first. With k equal to 1, the model reads only that document. Notice how close the three values are: 0.98, 0.96, 0.95. In two dimensions, many vectors point in similar directions. Real embeddings have hundreds of dimensions, so they can separate topics much better.

Step 3 · Sparse retrieval

The older method: count shared words, weighted by rarity

TF-IDF; an improved version, BM25, is still used in search engines

  • A word in every document does not help to choose one; a word in only one document points straight at it
  • tf, term frequency: how many times the word is in this document
  • idf, inverse document frequency: how rare the word is in all the documents

idf(word) = ln number of documentsdocuments that contain the word

tf-idf(word, doc) = tf(word, doc) × idf(word)

A document's score for a question: the sum of tf-idf over the question's words.

Before embeddings, retrieval worked by counting words. The best-known method is called TF-IDF. It is still widely used, often in an improved version called BM25.

The idea: look at which words the question shares with each document. But not every shared word is equally useful. Imagine you must find one person in a room, with one clue. If half the room has brown hair, "brown hair" does not help much. If only one person has a pet parrot, "pet parrot" finds them at once. Words work the same way. The word "the" is in almost every document, so it does not help us choose. A word that is in only one document points straight to it.

The score has two parts. TF, term frequency, counts how many times the word appears in one document. IDF, inverse document frequency, measures how rare the word is in the whole collection: the natural logarithm of the number of documents, divided by the number of documents that contain the word.

If the word is in every document, the fraction is 1, and the logarithm of 1 is 0. So a word that is everywhere adds nothing. If the word is in only one document, the fraction is large, and the score is high. The two parts are multiplied, so a word scores high only if it is in the document and rare in the collection.

TF-IDF, worked out

The five toy documents of Notebook 03b

Let's compute it on the five toy documents of the Retrieval Playground.

The word "model" is in three of the five documents: carbon, energy and retrieval. Its idf is the natural logarithm of 5 divided by 3. 5 divided by 3 is 1.67, and its logarithm is about 0.51.

The word "energy" is in only one document. Its idf is the logarithm of 5 divided by 1, the logarithm of 5, about 1.61.

Now look inside the energy document. Each of the two words appears there once, so tf is 1 for both. For "model": 1 times 0.51 is 0.51. For "energy": 1 times 1.61 is 1.61.

Both words appear once. But "energy" counts about three times more, because it is rare in the collection, and "model" is common.

Why the logarithm?

An imagined news archive with N = 1,000,000 articles

The word is inN ÷ that numberln of it

  • Without the logarithm, the rarest word counts 1,000 times more than a word in 1,000 articles: one rare word, even a typo, would decide the ranking
  • With it: 13.8 against 6.9, twice as much
  • A word in every article adds 0
  • With 5 documents the ratio is at most 5: the logarithm matters in large collections

Why is there a logarithm in the formula? To see why, we need a large collection. So imagine one, a news archive with one million articles. These numbers are made up.

A word in only one article: the ratio is one million divided by one, a million. A word in a thousand articles: one million divided by a thousand, which is a thousand. A word in every article: the ratio is one.

If we used the ratio directly, the rarest word would count a thousand times more than a word in a thousand articles. A single rare word, even a typo, would decide which article comes first. The other words of the question would hardly matter.

Now the last column, with the logarithm. The rarest word gets 13.8. The word in a thousand articles gets 6.9. The rare word still counts more, but about twice as much. And a word in every article gets the logarithm of one, which is zero. So words like "the" add nothing.

In a small collection the logarithm makes little difference: with five documents, the ratio is never larger than five. It matters in large collections, which is where real search happens.

Sparse and dense vectors

The picture of Session 1, now for whole documents

Sparse: one value per word of the vocabulary, mostly 0

  • Finds exact word matches only
  • Needs only counting

Dense: a few hundred learned values, all filled in

  • Matches different words with the same meaning
  • Needs an embedding model to run

The two questions of the notebook

questionwords shared with doc_energyfinds doc_energy?
A: how much energy does running a model useenergy, running, a, modelsparse ✓ · dense ✓
B: what does it cost in electricity to get an answeritsparse: a tie with two others · dense ✓

Here are the two kinds of document vectors side by side.

A sparse vector has one value for every word of the vocabulary. Most values are zero, because a document uses only a few of all possible words. Sparse retrieval can only match words that are exactly the same.

A dense vector has a few hundred values, and all of them are filled in. An embedding model learned these values from a large amount of text. Dense retrieval can match a question and a document that use different words for the same idea. The price is that it needs an embedding model to run. Sparse retrieval needs only counting.

The table shows the two questions of the notebook. Question A shares four words with the energy document, and both methods find it. Question B asks the same thing in other words. It shares only the word "it" with the energy document. Sparse retrieval ends in a tie between three documents. Dense retrieval still finds it, because electricity is close to energy.

Step 4 · What retrieval saves

Fewer tokens to read

Today's 26 documents, cut into tokens the way Qwen2.5 cuts them, without the question; top 2: the average over the 26 questions

  • Attention compares every token with every token: twice the tokens, four times the pairs (Session 1)
  • The rest of the model grows in step with the tokens
  • Writing the answer: one run of the model per written token, as many either way; only the attention to the input gets cheaper
  • So expect an energy saving smaller than the token saving: the notebook measures it

Why does reading fewer tokens save energy? Recall attention from Session 1. Every token is compared with every other token. Twice the tokens means four times the pairs.

The board works it out for today's collection. All 26 documents together are 4,031 tokens. The two documents the retriever picks are, on average over the 26 questions, about 310 tokens. 4,031 divided by 310 is about 13: thirteen times fewer tokens. The panel before showed one question at a time, with the question's own tokens included, so its numbers were a little different: for the PUE question, 4,040 and 355.

The pairs: 4,031 squared is about 16.2 million. 310 squared is 96,100. 16.2 million divided by 96,100 is about 169. So attention compares about 169 times fewer pairs.

But attention is only part of the work. Other parts of the model do an amount of work that grows in step with the number of tokens, not with the square. And writing the answer takes one run of the model for every token written, and the answer is about as long in both cases. Only the attention part of each run gets cheaper, because there are fewer input tokens in the KV cache to look at. So the energy saving will be smaller than the token saving. You will measure how much smaller this afternoon.

Long documents must be split

The embedding model reads at most 128 tokens

  • The rest of a document is cut off before its vector is computed: 23 of our 26 documents are longer than 128 tokens
  • Real systems split long documents into chunks, embed each chunk, and retrieve chunks; the chunk size is a design decision

One practical detail matters today. An embedding model can only read a limited number of tokens. Ours, MiniLM, reads at most 128. If a document is longer, the rest is cut off before the embedding is computed. So the embedding represents only the beginning of the document.

The chart shows our 26 documents. Press Play: MiniLM reads every document from its start, and where the 128-token window ends, the rest turns into hatching. The blue part of each bar is what MiniLM reads. The hatched red part is never seen. 23 of the 26 documents are longer than 128 tokens. For one of them, the answer to its quiz question is in the hatched part. You will see the retriever miss that question this afternoon.

Real systems solve this with chunking. They split each long document into smaller parts, called chunks, embed each chunk, and retrieve chunks. Choosing the chunk size is a design decision of its own.

Li, Li, Zhang, Mei & Bendersky, “Retrieval augmented generation or long-context LLMs? A comprehensive study and hybrid approach,” EMNLP 2024 Industry Track

Now some published evidence. A 2024 study from Google DeepMind and the University of Michigan compared the two approaches on three strong models: GPT-4o, GPT-3.5-Turbo and Gemini-1.5-Pro. Each question is about one long source text, for example a whole book or a long report.

Long context puts the whole source text into the prompt. In their two benchmarks, that is on average 7,000 words in one, and 100,000 tokens in the other. RAG cuts the text into chunks of 300 words and puts only the 5 most relevant chunks into the prompt. 5 times 300 is 1,500 words.

For all three models, long context gave better answers on average. So retrieval can lose some quality. But for 63 percent of the questions, the two approaches gave exactly the same answer. For those questions, reading everything bought nothing.

The authors used this to build a combined method, called Self-Route. The model first tries RAG, and also says whether the retrieved chunks are enough to answer. If yes, the RAG answer is used. If no, the question goes to long context. With Gemini-1.5-Pro, this cut the cost, the number of tokens the model reads, by 65 percent; with GPT-4o, by 39 percent. In both cases, the quality stayed close to long context.

The lesson: use the cheap method when it is enough, and the expensive one only when needed.

Retrieval adds a new way to fail. The baseline read every document, so the document with the answer was always in the prompt. A retriever can choose the wrong documents. Then the answer is not in the prompt at all. The model may say that the documents do not contain the answer. Or it may answer from a wrong document, and sound sure about it.

So when an answer is wrong today, there are two possible causes: the retriever fetched the wrong documents, or the model misread the right ones. The notebook measures the two separately. Retrieval accuracy says how often the right document was in the top k. Answer accuracy says how often the final answer was right.

The table shows retrieval accuracy on today's quiz, with k equal to 2. We computed it with the notebook's own models. The dense retriever finds the right document for 23 of the 26 questions. TF-IDF finds it for all 26.

And a question about RAG: there are two documents about RAG, and the other one ranks higher. On a small collection of short, clean documents on clearly different topics, counting words works very well. Real collections are larger and messier.

Retrieval is also used in machine translation. One method is called kNN-MT. kNN means k nearest neighbors. It starts with a translation model that is already trained, and adds a large datastore built from earlier translations. The datastore keeps, for every word of the earlier translations, the decoder state just before that word was written, and the word itself. Each time the model writes a word, it compares its current decoder state with the stored states, takes the k closest, looks at which words were written after them, and mixes those words into its own probabilities. It is the same idea as RAG, but it looks things up at every word, not once per question.

Real kNN-MT needs millions of entries and a lookup at every word. That is too big for a Colab session. We do a small version of the same idea, called a translation memory. Our memory has six Galician sentences from Speechwriter, each with an English translation.

We compute the embedding of our Galician passage, the one with "unha tía miña", and compare it with the six sentences. The table shows the cosine similarities. The most similar is the sentence about the cousin Fernando, with 0.40. That sentence and its translation go into the prompt as an example. Then the model translates our passage.

We compare the translations with and without the example, with the four metrics from the earlier sessions: BLEU, BERTScore, Qwen as a judge, and ChatGPT as a judge.
