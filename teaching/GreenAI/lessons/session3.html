  • First, find the documents most related to the question; then put them into the prompt, next to the question.
  • The model answers from the prompt and from what it learned in training
  • The facts only need to be in a document the retriever can find: a small model can answer about facts it never saw in training

Lewis et al., “Retrieval-augmented generation for knowledge-intensive NLP tasks,” NeurIPS 2020

The same idea in a chat assistant

The question: “How much energy does one Gemini prompt use?”

1. The model writes a search request: search("Gemini prompt energy")
2. The program around the model runs a web search and copies text from the top pages
3. The prompt now holds: the company's instructions + your question + the page text
4. The model writes the answer, with links to the pages it used
  • The model only writes text; a search request is text in a special format
  • It was trained on examples where a question about a specific or recent fact is followed by a search request
  • An uploaded file works the same way: cut into chunks, embedded, searched
  • Real systems add: approximate search over millions of chunks, word and embedding search together, a second model that reorders the top results

Dense retrieval

How a retriever finds documents

The cosine similarity of Topic 1, for whole texts

  1. Turn every document into a vector, an embedding. Once, in advance.
  2. Turn the question into a vector, with the same embedding model (ours: MiniLM, from Notebook 01c, trained so that texts with the same meaning get close vectors)
  3. Compare the question's vector with each document's: cosine similarity
  4. Keep the k most similar documents. Only those go into the prompt.

cos(q, d) = q · d|q| × |d|

  • q · d: multiply matching values, add them up
  • |q|: the length of the vector, √(sum of squares)
  • 1: the same direction; 0: a right angle; below 0: pointing away

Sparse retrieval

The older method: count shared words, weighted by rarity

TF-IDF; an improved version, BM25, is still used in search engines

  • A word in every document does not help to choose one; a word in only one document points straight at it
  • tf, term frequency: how many times the word is in this document
  • idf, inverse document frequency: how rare the word is in all the documents

idf(word) = ln number of documentsdocuments that contain the word

tf-idf(word, doc) = tf(word, doc) × idf(word)

A document's score for a question: the sum of tf-idf over the question's words.

Why the logarithm?

An imagined news archive with N = 1,000,000 articles

The word is inN ÷ that numberln of it
1 article1,000,00013.8
1,000 articles1,0006.9
every article10
  • Without the logarithm, the rarest word counts 1,000 times more than a word in 1,000 articles: one rare word, even a typo, would decide the ranking
  • With it: only twice as much
  • With 5 documents the ratio is at most 5: the logarithm matters in large collections

Sparse and dense vectors

The picture of Topic 1, now for whole documents

Sparse: one value per word of the vocabulary (its tf-idf in the document), mostly 0

  • Finds exact word matches only
  • Needs only counting

Dense: a few hundred learned values, all filled in

  • Matches different words with the same meaning
  • Needs an embedding model to run

What retrieval saves

Fewer tokens to read

The 26 documents, cut into tokens the way Qwen2.5 cuts them, without the question; top 2 by the dense retriever: the average over the 26 questions (TF-IDF's: 311)

  • Attention compares every token with every token: twice the tokens, four times the pairs (Topic 1)
  • The rest of the model grows in step with the tokens
  • Writing the answer: one run of the model per written token, as many either way; only the attention to the input gets cheaper
  • So expect an energy saving smaller than the token saving: the notebook measures it

Long documents must be split

The embedding model reads at most 128 tokens

  • The rest of a document is cut off before its vector is computed: 23 of our 26 documents are longer than 128 tokens
  • Real systems split long documents into chunks, embed each chunk, and retrieve chunks; the chunk size is a design decision

What can go wrong

The retriever can miss

Then the answer is not in the prompt at all

  • The baseline read every document: the right one was always in the prompt
  • Now a wrong answer has two possible causes: the retriever, or the model
  • Retrieval accuracy: how often the right document is in the top k
  • Answer accuracy: how often the final answer is right

Retrieval works for translation too

kNN-MT: a lookup at every word

  • At each word it writes, it compares its decoder state with the states stored from earlier translations
  • It mixes the words written after the k closest states into its own probabilities
